# AV Numbers — 公開設計（Cloudflare）

このアプリを Cloudflare を使って世の中に公開するための設計。現時点では**設計・方針のみ**で、実際のデプロイ作業（Cloudflareアカウントでの操作、公開URLの発行）はまだ行っていない。

## 1. 前提となるアプリの性質

- サーバーサイド処理を持たない、**完全に静的なクライアントサイドアプリ**
  - 問題生成・採点・演算エンジンはすべてブラウザ内のJavaScriptで完結する（`AV_Numbers_prototype_v9.html`）
  - 進捗（解放ステージ・ベストスコア）は `localStorage` に保存されるのみで、外部DBやAPIには依存しない
- ビルドツールチェーンも現状なし（単一HTMLファイル）

この性質から、バックエンド実行環境（Cloudflare Workers）は初期版では不要で、**Cloudflare Pages によるホスティングのみ**で要件を満たせる。

## 2. 採用方針：Cloudflare Pages

| 項目 | 方針 |
| --- | --- |
| ホスティング | Cloudflare Pages（静的サイト） |
| ソース連携 | GitHubリポジトリと連携し、`main` ブランチへのpushで自動デプロイ |
| ビルドコマンド | なし（静的ファイルをそのまま配信） |
| 出力ディレクトリ | 公開ルート（後述の構成変更後は `public/` を想定） |
| バックエンド | 不要（Workers/D1/KVは将来拡張の候補として保留） |
| 独自ドメイン | 任意。初期は Cloudflare Pages が発行する `*.pages.dev` サブドメインで公開する |

Cloudflare Pages を選ぶ理由：

- 静的サイトのホスティングに特化しており、現状のアプリ構成（ビルド不要・単一HTML）と相性が良い
- GitHub連携によりpushするだけで公開・更新が完結し、デプロイ運用のコストが低い
- 無料枠で個人プロジェクトの公開に十分
- 将来、逆算問題の判定や共有ランキングなど**サーバー側処理が必要になった場合**、同じCloudflareエコシステム内で Pages Functions / Workers へ自然に拡張できる

## 3. 公開前に整理したいリポジトリ構成

現状は単一HTMLがリポジトリ直下にある。Cloudflare Pages で公開する際は、公開物と設計ドキュメント・将来のソース分割を区別するため、以下のような構成を想定する。

```text
.
├── public/                        # Cloudflare Pages の公開ルート
│   └── index.html                 # AV_Numbers_prototype_v9.html をリネーム/移設したもの
├── docs/
│   ├── DESIGN.md
│   ├── GAME_DESIGN.md
│   ├── DEPLOYMENT.md
│   └── ANIMATION.md
└── README.md
```

- `AV_Numbers_prototype_v9.html` を `public/index.html` としてそのまま配信する形にするか、`src/` を設けて演算エンジン・出題生成・UIをファイル分割するかは、[GAME_DESIGN.md の実装方針](./GAME_DESIGN.md)（テスト整備）と合わせて検討する
- ファイル分割を行う場合でも、ビルドステップなし（ブラウザがそのまま解釈できるJS/CSS）を維持するか、簡易バンドラを導入するかは別途判断する

## 4. デプロイ手順（実行時のチェックリスト）

実際に公開作業を行う際の想定手順。**GitHubへのリポジトリ作成・push、Cloudflareアカウントでの設定は公開範囲に影響する操作のため、実行前に必ずユーザーの確認を取る。**

1. ローカルをGitリポジトリ化し、GitHub上にリポジトリを作成してpushする
2. Cloudflareダッシュボードで Pages プロジェクトを新規作成し、GitHubリポジトリと連携する
3. ビルド設定：Framework preset は `None`、ビルドコマンドは空、出力ディレクトリは `public`（または公開物の配置先）を指定する
4. デプロイ完了後、発行された `*.pages.dev` のURLで動作確認する
5. 必要であれば独自ドメインをPagesプロジェクトに追加する
6. 以降は `main` ブランチへのpushで自動的に再デプロイされる

## 5. 公開にあたっての確認事項

- ゲームタイトル・コンセプトを公開して問題ないか（現時点では非公開の個人プロジェクトという前提で進めている）
- `localStorage` のみで進捗管理しているため、**ユーザーごとの進捗はブラウザ・端末をまたいで共有されない**。この制約を公開後も許容するか、将来的にアカウント機能やクラウド同期（Workers + D1など）を検討するかは別トピックとする
- アクセス解析は導入する（[6節](#6-アクセス解析cloudflare-web-analytics-を採用)参照）。エラーモニタリングを入れるかどうかは初期版では未定

## 6. アクセス解析：Cloudflare Web Analytics を採用

「誰が」までは不要で、匿名の集計データ（アクセス数・傾向）が見られれば十分という前提のもと、**Cloudflare Web Analytics**（無料）を採用する。

- 取得できるもの：訪問数・ページビュー数の推移、参照元、ブラウザ/OS、アクセス元の国、ページ読み込み速度（Core Web Vitals）
- 取得できないもの：個々の訪問者を識別する情報（IPアドレスなど）。Cookie不要・個人を特定しない設計のため、そもそも記録されない
- ダッシュボード上で確認できるのは**直近7日分のみ**。それより長い期間の推移を見たくなった場合は、別途エクスポート手段を検討する
- 有効化方法：Cloudflare Pagesのプロジェクト設定から「Web Analytics」を有効にするだけで、コード側の変更はほぼ不要（自動でビーコンが挿入される）
- この用途では、生のアクセスログ（IP・タイムスタンプ付きの1件ごとの記録。Enterpriseプラン向けのLogpushが必要）や、ゲームプレイ内容そのもののログ（どのステージを何回遊んだか等。Workers/D1など専用の実装が必要）までは対応しない

## 7. 将来拡張の候補（現時点では未採用）

- **Cloudflare Workers**：逆算問題の出題ロジックをサーバー側に置く、不正な進捗改ざんを防ぐ、ゲームプレイ内容のログを取る、といった要件が出た場合の候補
- **Cloudflare D1 / KV**：ステージ進捗・ベストスコアをアカウント単位でクラウド保存する場合の候補
- これらは「静的サイトで完結する」という現在の設計方針を変える意思決定になるため、必要性が明確になった時点で改めて設計する
