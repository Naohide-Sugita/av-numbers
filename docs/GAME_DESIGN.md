# AV Numbers — ゲーム設計（初期版）

ゲームモードは1つに絞り、10問1セットのステージを順番にクリアしていく。数の3状態（`v / 無印 / A`）と演算の仕様は [DESIGN.md](./DESIGN.md) を参照。

> 現行プロトタイプ（[`AV_Numbers_prototype_v9.html`](../AV_Numbers_prototype_v9.html)）は本ドキュメントの内容を実装済み。旧バージョンとの経緯は [15. プロトタイプとの差分](#15-プロトタイプとの差分)を参照。

## 1. 基本ゲームループ

- 1ステージ = 10問
- 10問中 **8問以上正解でクリア**
- 7問以下の場合は、そのステージを最初からやり直す
- 問題は毎回ランダム生成する
- 同じ10問セット内では、同一の式を重複させない
- クリアすると次のステージを解放する
- 一度クリアしたステージはいつでも再挑戦できる

## 2. ステージ構成

初期版は**全3ステージ**構成とする（旧8ステージ案から圧縮）。1ステージ=10問・8問以上正解でクリアというゲームループ（1節）は変わらないが、ステージごとに「1つのテーマだけを扱う」のではなく、**1ステージの中で難易度を段階的に上げていく**構成にする。

### Stage 1：2項計算（片側・両側marks／足し算・引き算）

2項計算に関する基本要素（片側marks・両側marks × 足し算・引き算）を、この1ステージの中だけで段階的にすべて経験させる。最初の2〜3問で操作に慣れたら、以降は1問ごとに新しい要素を1つずつ追加していく。

想定する段階配分（目安。実際の出題数は実装時に微調整してよい）：

- 1〜2問目：片側marksの足し算のみ（易）。例：`2v + 3 = ?`
- 3〜4問目：片側marksの引き算を導入。例：`5 - 3v = ?`
- 5〜7問目：両側marksの足し算（相殺・正規化を含む）。例：`2v + 3A = ?`、`2A + 3A = 6v`
- 8〜10問目：両側marksの引き算。例：`5A - 3v = ?`

### Stage 2：3項以上の複合計算

足し算・引き算が混在する3項以上の式を扱う。例：`2v + 3A - 1 = ?`、`5A - 2v + 1A = ?`

片側・両側marksの扱い自体はStage 1で経験済みのため、Stage 2では「項数が増えることで、複数の状態作用を順番に追う」難しさに焦点を当てる。

### Stage 3：逆算（穴埋め問題）

2項の式の左右どちらかの項を `?` にした逆算問題のみを扱う（3項以上の逆算は今回のスコープ外）。例：`2A + ? = 6v`、`? + 3v = 5A`、`5 - ? = 2A`、`? - 3v = 2A`

狙いは、順方向に答えを出すだけでなく、結果から必要な位置を逆向きに考えること。詳細な出題生成・表示・回答UI・不正解時の解説は [16. Stage 3：逆算の設計](#16-stage-3逆算の設計)にまとめる。

初期版は **Stage 1〜3** で完結とする。Stage 3クリア後は、好きなステージを再挑戦し、各ステージの `10/10 Perfect` を目指せるようにする。

## 3. 問題生成ルール

- 基礎ステージで使用する整数は原則 `1〜9`
- 答えの整数部は `0〜9` に収める
- 負の答えは出さない
- `0v / 0 / 0A` は許容する
- 同一セット内で同じ式は重複させない
- ステージを再挑戦した場合は、以前出た問題が再登場してもよい

### 出題設計・難易度曲線

各ステージの10問は、式を完全ランダムに並べるのではなく、**プレイヤーに体験させたい現象を先に決め、その条件を満たす式をランダム生成する**。狙いは、難易度を上げることよりも、AV Numbersの数理構造を順番に発見させること。

基本の発見順は次の通り。

1. **移動**：片側の `A / v` が答えを右・左へ1つ動かす
2. **相殺**：左右の逆向き作用が打ち消し合う
3. **正規化**：左右の同方向作用が重なり、2段移動で表記が切り替わる
4. **反転**：引き算では右側の状態作用が反転する
5. **複合**：左右の状態と引き算の反転を同時に読む
6. **連鎖**：3項以上の式で、複数の状態作用を順番に追う
7. **連続反転**：足し算・引き算が混ざる長い式で、作用方向の切り替えを追う

代表問題は次の通り（[2節](#2-ステージ構成)の新しい3ステージ構成に対応）。

- Stage 1（1〜2問目）：`2v + 3 = 5v` のような1ステップ移動
- Stage 1（3〜4問目）：`5 - 3v = 2A` のような右側状態の反転（引き算導入）
- Stage 1（5〜7問目）：`2v + 3A = 5` のような相殺、`2A + 3A = 6v` のような正規化
- Stage 1（8〜10問目）：`5A - 3v = 3v`、`5v - 3A = 1A` のような左右作用の複合（引き算×両側marks）
- Stage 2：`2v + 3A + 1 = ?`、`5A - 2v + 1A = ?` のような3項以上の連鎖
- Stage 3：`2A + ? = 6v`、`5 - ? = 2A` のような逆算

### Stage 1の10問配分

Stage 1は、単なるランダム出題ではなく、[2節](#stage-12項計算片側両側marks足し算引き算)の段階配分（1〜2／3〜4／5〜7／8〜10問目）に沿って**新しい要素を1問ごとに1つずつ追加**する構成にする。

各段階の**状態パターン（片側/両側 × 足し算/引き算のどれを扱うか）を先に決め、整数値は条件を満たす範囲でランダム生成する**。整数値そのものより、要素をどの順番で追加していくかを出題設計の主役にする。

## 4. 回答入力UI

プレイヤーの思考順に合わせて、**「普通の数字だけで計算 → 状態分だけ左右へ移動」**の2段階で回答する。

### ① 基準値を入力

- まず `v / A` を無視し、整数部分だけで普通に計算した答えを数字パネル `0〜9` から入力する
- 数字キーはスマホで慣れた3列テンキー配置にする：`1 2 3 / 4 5 6 / 7 8 9 / ⌫ 0`
- 数字は1桁に制限せず、押した順に連結して2桁以上も入力できるようにする。例：`1` → `2` で `12`
- `⌫` は末尾の1桁を削除する。すべて削除した場合は未入力状態に戻す
- 数字を追加・削除して基準値を変更した場合、左右移動は基準位置からやり直す
- `OK` は数字キー群とは分けて、下部に横幅いっぱいで配置する
- 例：`2A + 3A` なら、最初に `2 + 3 = 5` と考えて `5` を入力する

### ② 左右へ移動

- 基準値を入力した後、数直線上の現在値を `← / →` で1段ずつ動かす
- `←` = 左へ1段、`→` = 右へ1段
- 例：`2A + 3A` は `5` から右を2回押して `5 → 5A → 6v`
- 引き算でも同じUIを使い、右側の状態は作用方向を反転して判断する
- 例：`5 - 3v` は基準値 `2` を入力し、右を1回押して `2A`

### 回答確定

- `OK` で回答確定
- 正誤判定では、最終位置だけでなく**最初に入力した基準値も正しいこと**を確認する
- これにより、ゲームの操作そのものを「普通に計算してから状態分だけ動かす」という解法と一致させる
- **通常の計算画面はスマホの1画面内で完結させ、回答のための縦スクロールを発生させない**
- 問題式・基準値入力・左右移動・数字キー・OKまでを同一ビューポート内に固定し、画面高が低い端末では余白・カード高・キー高を縮めて対応する

## 5. 正解・不正解時の挙動

### 正解
- 軽い正解演出を表示
- 約0.5秒後に自動で次の問題へ進む

### 不正解
- 正解を表示
- 簡単な解説を表示
- ユーザーが「次へ」を押して次問へ進む

## 6. 不正解時の解説方針

通常プレイとチュートリアルでは、`1/3` を前面に出さず、**位置の移動**として理解させる。表向きのルールは次の2つ。

- `A` = 右へ1つ
- `v` = 左へ1つ

まず整数部分の基準計算を行い、その後に `v / A` の作用を数直線上で1つずつ反映する。

### 数直線アニメーション

不正解時は、必要に応じて **数直線上でカーソルが1ステップずつ移動するアニメーション**を表示する。目的は、`v / A` の作用と、特に引き算で方向が反転する感覚を視覚的に理解させること。

例：`5A - 3v = ?`

1. まず基準計算 `5 - 3 = 2` を表示する
2. `5A` の `A` を強調し、カーソルを右へ1つ動かす
3. `3v` の `v` を強調し、「小さい数を引く」ためさらに右へ1つ動かす
4. 最終位置 `3v` で停止し、正解として表示する

### 詳しい仕組み

`Rules` 内の「詳しい仕組み」を開いた場合のみ、数学的定義を表示する。

```text
nv = n - 1/3
nA = n + 1/3
```

例：`7A - 3v`

```text
7A = 7 + 1/3
3v = 3 - 1/3

(7 + 1/3) - (3 - 1/3)
= 4 + 2/3
= 5v
```

つまり、**遊ぶときは位置パズル、詳しく知りたい人には1/3による数学的定義**という二層構造にする。

## 7. チュートリアル

初回のみ、短い操作型チュートリアルを表示する。

各画面では、**その画面で何を理解すれば次へ進んでよいかを1つだけ明示する**。さらに説明を読むだけではなく、その理解に対応する操作を1回実行してから「次へ」を有効にする（画面0はコンセプトを伝えるための例外。詳細は後述）。チュートリアルは導入1画面＋操作3画面に絞り、通常プレイと同じ「普通の答えを出す → 左右へ動かす」という操作順をそのまま教える。

また、**左右の矢印は数直線上の移動操作だけに使用する**。ページ送り・「次へ」・「わかった」など、数の移動と無関係な操作には矢印記号を使わない。これにより、`← / →` の意味を「左へ1段 / 右へ1段」に固定する。

### 画面0：コンセプトの紹介

チュートリアルの一番最初に、操作理解ではなく**このゲームの着想（コンセプト）を伝えるだけ**の導入画面を置く。演算ロジックの理解を問う画面ではないため、他の画面とは扱いが異なる。

- 見せるもの：子どものシルエットのイラストと、次の3つの例文（言葉のみで表記し、`1A` のような記号表記はまだ使わない）
  1. 「大きい1 ＋ 1 ＝ 大きい2」
  2. 「小さい1 ＋ 小さい1 ＝ 大きい1」
  3. 「大きい1 ＋ 小さい1 ＝ 2」
- 冒頭に一言、着想元を明示する：「5歳の子どもの、こんな発想がヒントになっています。」
- 3つの例文は子どものシルエットと合わせて、**自動アニメーションで1つずつ順番に**表示する（タップして進める形にはしない）
- 3つの例文が出そろった後、最後のビートとして橋渡しの一文を表示する：「この発想から、数字が『小さい・普通・大きい』の3つの状態を持つ、というゲームが生まれました。」（＝着想〈子どもの発言〉→発明〈数字に状態を持たせるという仕組み〉という2段構造を、画面0の中だけで完結させる）
- この画面で伝えること：**このゲームは、子どもの素朴な発想から生まれた**という雰囲気・世界観と、「数字が状態を持つ」というゲームの核になるアイデア。`v / A` の記号や計算ロジックの理解はここでは求めない
- 「次へ」は、橋渡しの一文まで含めた表示が一通り終わったタイミングで有効になる（他の画面のような「操作の正しさ」を問う条件ではなく、アニメーションの完了を条件にする）
- 上記3つの例文はすべて、実際のルール上も正しい計算になるように選んでいる（2つ目の「小さい1＋小さい1＝大きい1」は `1v + 1v = 1A` に相当し、後述の「正規化」という現象を、理由の説明なしに一足先に体感させる）

### 画面1：位置だけ覚える
- 見せるもの：数直線 `1 → 1A → 2v → 2`
- 操作：`A / v` を押すとカーソルが実際に1マスずつ動く
- この画面で理解すること：**`A` は右へ1つ、`v` は左へ1つ**
- 画面下に「ここで覚えること」を固定表示する

### 画面2：普通の答えから動かす
- 見せるもの：`2v + 3 = ?`
- まず `2 + 3 = 5` を表示し、その後 `5 → 5v` をアニメーションする
- この画面で理解すること：**まず普通に計算し、そのあと `v / A` の分だけ動かす**

### 画面3：引き算は向きに注意（反転）
- 見せるもの：`5 - 3v = ?`
- `5 - 3 = 2` の後、`2 → 2A` をアニメーションする
- この画面で理解すること：**小さい数を引くと、答えは大きくなる**

### 画面4：実際に解く
- Stage 1相当の問題を1問解かせる
- 正解したらチュートリアル完了

`次へ` は単なるページ送りではなく、その画面の理解（または画面0では紹介）を確認する区切りとして使う。必要に応じて `わかった →`、`試してみる →` のように文言を変える。

チュートリアルでは `1/3` を表示しない。数学的定義は `Rules > 詳しい仕組み` で見せる。

## 14. 設計方針

- ゲームモードは増やさない
- ルール自体が新しいため、ゲーム操作はできるだけ単純にする
- 難易度はモードではなくステージ進行で上げる
- `v / A` が付くのは **数字のみ**。演算子は通常の `+ / -` に限定する
- 演算子状態は、数字側の状態と独立した意味を持たせられず数字側へ還元できるため採用しない
- プレイヤーが「答えを選ぶ」のではなく、**自分で答えを組み立てる**ことをゲーム体験の中心にする
- プレイヤー向けの表現は「分数計算」ではなく、**数直線上の位置・1ステップ移動**を中心にする
- `1/3` は隠すのではなく、`Rules > 詳しい仕組み` に数学的裏付けとして残す

## 16. Stage 3：逆算の設計

[2節](#stage-3逆算穴埋め問題)で定義したStage 3（2項の逆算・穴埋め問題）の、出題生成・表示・回答UI・不正解時の解説をまとめる。既存の順算（Stage 1・2）のロジックとUIを最大限流用し、新規実装を最小限にする方針で設計している。

### 16.1 出題生成

1. まず通常の2項の順算問題（既知の2項＋計算結果）を、[3節](#3-問題生成ルール)と同じ制約（整数は`1〜9`、答えの整数部は`0〜9`、負の答えなし）で生成する。これは既存の出題生成ロジック（`makeQuestion` 相当）をそのまま使える
2. 生成した式の左右どちらか一方の項をランダムに選び、`?` に置き換えて隠す。もう一方の項（既知項）と計算結果（ターゲット）はそのまま表示する
3. これにより、「`?`の位置（左/右） × 演算子（`+`/`-`）」の4パターンすべてが自然にカバーされる
4. 例：`2A + ? = 6v`（右が空欄・足し算）、`? + 3v = 5A`（左が空欄・足し算）、`5 - ? = 2A`（右が空欄・引き算）、`? - 3v = 2A`（左が空欄・引き算）

この方法により、順算問題として生成された時点で既に整数範囲・答えの範囲などの制約を満たしているため、逆算専用の範囲チェックを新たに設計する必要がない。

### 16.2 表示形式

- 式は「既知項 `op` `?` `=` ターゲット」または「`?` `op` 既知項 `=` ターゲット」の形で表示する
- `?` は答えが確定するまで状態が分からないため、`v / A` のような色付き記号は付けず、無色のプレースホルダーとして表示する

### 16.3 回答UI

[4節](#4-回答入力ui)の既存2段階UI（①基準値入力 → ②矢印で移動）をそのまま使う。

- ① 基準値入力：**式全体の記号（`v / A`）を無視して**計算した場合に `?` に入る数を入力する
  - 例：`2A + ? = 6v` → 記号を無視すると `6 - 2 = 4` なので `4` を入力する
  - 例：`5 - ? = 2A` → 記号を無視すると `5 - 2 = 3` なので `3` を入力する
  - 例：`? - 3v = 2A` → 記号を無視すると `2 + 3 = 5` なので `5` を入力する
- ② 矢印で移動：入力した基準値から、`← / →` で正しい答え（`?` の状態を含む値）に一致する位置まで動かす
- 正誤判定は既存と同じく、**基準値と最終位置の両方が正しいこと**を確認する

上記①の「記号を無視した式」は、既知項とターゲットの表示上の整数部分だけを使い、`?` の位置と演算子に応じて次のように計算する（実装時の参考）。

| `?`の位置 | 演算子 | 記号を無視した式 |
| --- | --- | --- |
| 右（`known + ? = target`） | `+` | `?_base = target_int - known_int` |
| 左（`? + known = target`） | `+` | `?_base = target_int - known_int` |
| 右（`known - ? = target`） | `-` | `?_base = known_int - target_int` |
| 左（`? - known = target`） | `-` | `?_base = target_int + known_int` |

`target_int` / `known_int` は、それぞれの項の表示上の整数部分（`v / A` を無視した数字）。②の矢印移動は、既知項とターゲットを実際の位置（1/3刻み）で捉え、`?`の正しい位置との差分だけ移動させれば良く、順算と同じ「矢印を押した回数がそのまま状態のズレになる」仕組みがそのまま成立する。

### 16.4 不正解時の解説

[6節](#6-不正解時の解説方針)の数直線アニメーションを拡張する。

- 既知項とターゲット（計算結果）を、数直線上の2つの点として表示する
- 「既知項の位置」から「ターゲットの位置」までカーソルが移動する様子をアニメーションし、その移動量がそのまま `?` の答えであることを示す
- 演算子（`+`/`-`）と `?` の位置に応じて、移動の起点・向きが変わる。具体的な起点・向きの算出は、既存の `effectData` 関数と同様の考え方で式ごとに計算する（[ANIMATION.md](./ANIMATION.md)側の実装検討事項）
